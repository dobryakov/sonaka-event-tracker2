# Feature Specification: Приёмка и учёт событий от внешних клиентов

**Feature Branch**: `001-http-event-ingestion`  
**Created**: 2026-04-15  
**Status**: Draft  
**Input**: User description: "Атрибуты трекинга (system_name, object_id, event_name, metadata как структурированные данные, event_time); сервер с HTTP-приёмкой; клиенты по HTTP; запуск клиентов через compose exec с завершением процесса; автотесты отправляют событие и проверяют его наличие в хранилище запросом к данным; документация: установка, первый запуск, примеры клиентов со случайными данными, примеры автотестов."

## Clarifications

### Session 2026-04-15

- Q: Какое хранилище событий обязательно для этой фичи? → A: PostgreSQL как единственное поддерживаемое постоянное хранилище (вариант A).
- Q: Нужна ли аутентификация или авторизация на HTTP-приёмке в объёме фичи? → A: Нет, приёмка без auth в доверенном контуре (вариант A).
- Q: В каком виде клиент MUST передавать `event_time` в контракте приёмки? → A: Строка RFC 3339 / ISO 8601; при несоответствии — поведение по допущениям (вариант A).
- Q: Тело успешной приёмки события MUST быть? → A: Один JSON-объект с `Content-Type: application/json` (вариант A).
- Q: Что MUST возвращать сервер при успешной приёмке? → A: HTTP 2xx и JSON с уникальным `id` записи в PostgreSQL (вариант A).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Отправка события из внешней системы (Priority: P1)

Интегратор или внешняя система отправляет описание произошедшего события в центральный сервис приёмки, чтобы зафиксировать факт, объект, контекст и время для последующего анализа и расследований.

**Why this priority**: Без приёмки и сохранения событий нет ценности продукта; это минимально жизнеспособный результат.

**Independent Test**: Можно полностью проверить отправкой одного корректного сообщения с обязательными полями и убедившись, что запись с теми же логическими значениями доступна для проверки в хранилище событий.

**Acceptance Scenarios**:

1. **Given** сервис приёмки доступен по сети, **When** клиент отправляет один JSON-объект (`Content-Type: application/json`) с заполненными `system_name`, `object_id`, `event_name`, допустимыми структурированными `metadata` и согласованным `event_time`, **Then** система принимает запрос, сохраняет ровно одну запись события с этими атрибутами и отвечает кодом 2xx с JSON-телом, содержащим `id`, совпадающий с первичным ключом сохранённой строки в PostgreSQL.
2. **Given** клиент повторно отправляет эквивалентное событие (повторная доставка), **When** каждый такой запрос успешно обработан, **Then** в истории событий сохраняется отдельная запись на каждую успешную доставку (дедупликация не применяется в объёме этой фичи).

---

### User Story 2 - Контроль качества сквозной цепочки (Priority: P2)

Команда разработки или эксплуатации запускает автоматизированную проверку: отправка тестового события и подтверждение, что оно действительно оказалось в постоянном хранилище.

**Why this priority**: Снижает риск регрессий и даёт уверенность, что приёмка и персистентность работают вместе.

**Independent Test**: Запуск одного пакета автопроверок без ручных шагов, завершающийся отчётом об успехе или явной ошибке.

**Acceptance Scenarios**:

1. **Given** развёрнуты сервис приёмки и PostgreSQL с данными событий, **When** автотест отправляет событие с заранее известными значениями полей, **Then** ответ приёмки содержит JSON с `id` сохранённой записи и проверка через SQL-запрос к PostgreSQL находит ту же строку по этому `id` с теми же значениями `system_name`, `object_id`, `event_name`, `metadata` и `event_time` (сравнение момента времени — с нормализацией к UTC и учётом правил для fallback из раздела «Допущения»).
2. **Given** автотесты интегрированы в стандартный контур поставки проекта, **When** выполняется регрессия после изменений, **Then** несоответствие между принятым событием и данными в хранилище приводит к явному падению проверки.

---

### User Story 3 - Быстрый старт для разработчиков и операторов (Priority: P3)

Новый участник поднимает окружение, запускает клиентские примеры и видит событие в системе, опираясь только на документацию репозитория.

**Why this priority**: Ускоряет внедрение и снижает число обращений за устными инструкциями.

**Independent Test**: Человек без предметного контекста следует документу «установка и первый запуск» и получает успешно принятое событие.

**Acceptance Scenarios**:

1. **Given** документация опубликована в репозитории, **When** читатель выполняет шаги установки и первого запуска в среде проекта, **Then** он может однозначно воспроизвести работающую связку «клиент → приёмка → запись в хранилище».
2. **Given** документация содержит раздел примеров, **When** пользователь запускает примеры отправки с псевдослучайными значениями полей через предписанный способ вызова в контейнерной среде, **Then** команды из документа выполняются без догадок и завершают процесс клиента после отправки.
3. **Given** документация описывает автопроверки, **When** пользователь запускает их тем способом, который указан в документации, **Then** он получает понятный вывод о прохождении или ошибке.

---

### Edge Cases

- Отсутствует одно или несколько обязательных полей (`system_name`, `object_id`, `event_name`, `event_time`) — система отклоняет приёмку с понятной для клиента индикацией ошибки.
- `metadata` не удаётся разобрать как допустимую структурированную полезную нагрузку в формате приёмки — отклонение с индикацией ошибки.
- Тело запроса не является корректным JSON, отсутствует `Content-Type: application/json` или тип не `application/json` — отклонение с индикацией ошибки.
- Слишком большой объём тела запроса — отклонение или обрыв с безопасным ограничением размера (конкретный предел задаётся на этапе планирования реализации).
- Недоступно хранилище или сбой записи — клиент получает ошибку, данные не считаются принятыми.
- `event_time` не удаётся разобрать как корректную строку RFC 3339 / ISO 8601 — сохраняется время приёма на стороне сервиса (см. допущения); клиенту возвращается успешный приём, если остальные поля валидны.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять сетевой интерфейс приёмки событий по протоколу HTTP для вызывающих сторон внутри контуров развёртывания проекта.
- **FR-002**: Для каждой успешно принятой заявки система MUST сохранять в PostgreSQL запись события с атрибутами: имя системы-отправителя (`system_name`, текст), идентификатор объекта наблюдения (`object_id`, текст), имя типа или экземпляра события (`event_name`, текст), произвольные структурированные метаданные (`metadata`) с поддержкой вложенности и типизированных значений в согласованном машиночитаемом формате, отметка времени события (`event_time`): в запросе — строка RFC 3339 / ISO 8601; при успешном разборе сохраняется соответствующий момент времени, при неуспешном — момент приёма запроса на сервере.
- **FR-003**: Клиентские программы MUST взаимодействовать с приёмкой только через этот HTTP-интерфейс (без альтернативных каналов в объёме этой фичи).
- **FR-004**: Запуск клиентских примеров MUST выполняться единообразным способом, задокументированным для контейнерной среды проекта, так чтобы клиентский процесс завершался после отработки сценария отправки.
- **FR-005**: Автоматизированные приёмочные тесты MUST отправлять событие в приёмку и MUST подтверждать наличие именно этой записи в PostgreSQL посредством SQL-запроса (чтение сохранённого состояния), сопоставляя `id` из успешного ответа приёмки с первичным ключом строки в БД, без ручной проверки.
- **FR-006**: Документация MUST включать: установку и первый запуск; примеры запуска клиентских сценариев с псевдослучайными значениями полей события; примеры запуска автотестов.
- **FR-007**: Постоянное хранилище записей событий в объёме этой фичи MUST быть PostgreSQL; поддержка других СУБД или нереляционных хранилищ вне объёма.
- **FR-008**: Эндпоинт приёмки событий в объёме этой фичи MUST быть доступен без аутентификации и авторизации вызывающих сторон; ограничение доступа обеспечивается контуром развёртывания, а не механизмами этой фичи.
- **FR-009**: Запрос приёмки MUST иметь тело в виде одного JSON-объекта и заголовок `Content-Type: application/json`. Поля `system_name`, `object_id`, `event_name`, `event_time` и `metadata` MUST располагаться на верхнем уровне этого объекта; `metadata` MUST быть JSON-объектом или JSON-массивом (вложенная структура в рамках JSON).
- **FR-010**: При успешной приёмке система MUST ответить кодом из класса 2xx, с телом `Content-Type: application/json`, содержащим поле `id` с уникальным значением, совпадающим с первичным ключом соответствующей строки события в PostgreSQL.

### Key Entities *(include if feature involves data)*

- **Событие (Event)**: Единица учёта факта, произошедшего с объектом; характеризуется устойчивым идентификатором записи (`id` в PostgreSQL и в успешном ответе приёмки), отправителем, объектом, именем события, метаданными и временем; хранится для последующего поиска и отчётности.
- **Клиент отправки**: Внешняя или тестовая программа, формирующая и передающая событие в приёмку по HTTP.
- **Хранилище событий**: База данных PostgreSQL, обеспечивающая долговременное сохранение и выборку записей событий для проверок и аналитики.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В контролируемой среде 100% валидных тестовых отправок из автопроверок приводят к обнаружению соответствующей записи в хранилище не позднее чем через 5 секунд после успешного ответа приёмки.
- **SC-002**: Новый участник, следуя только документации первого запуска, сообщает о первом успешно принятом событии не более чем за 30 минут при стандартной машине разработчика и типовом подключении к сети.
- **SC-003**: В регрессионном прогоне автопроверок не менее 95% сценариев с корректным составом полей завершаются успешным приёмом при штатной доступности зависимостей (хранилище и сеть в норме).
- **SC-004**: Для каждой обязательной операции из документации (установка, пример клиента, запуск автотестов) существует воспроизводимая команда или последовательность без недекларированных предварительных шагов; нарушение этого правила считается дефектом документации.

## Assumptions

- Граница доверия: интерфейс приёмки рассчитан на использование внутри контролируемого контура развёртывания; аутентификация и авторизация вызывающих сторон на HTTP-приёмке в объёме этой фичи не реализуются (зафиксировано в FR-008).
- `event_time` в теле запроса — строка RFC 3339 / ISO 8601 (с суффиксом `Z` или числовым смещением от UTC). При успешном разборе в колонке хранится этот момент (нормализация к UTC на усмотрение реализации и схемы БД); при неуспешном разборе в колонке фиксируется время приёма запроса на сервере, запись считается принятой при прочих валидных полях.
- Формат тела запроса приёмки зафиксирован в FR-009 (JSON); при успешной приёмке ответ обязан содержать `id` записи (FR-010). Конкретный код 2xx, дополнительные поля успешного ответа, коды и структура JSON при ошибках уточняются в техническом плане/контракте так, чтобы ошибки клиента были машиночитаемыми.
- Идемпотентность и дедупликация событий не требуются, если отдельно не согласовано: повторные доставки могут порождать отдельные записи.
- Проект поставляется в контейнеризованном виде; в документации для запуска примеров клиентов используется разовый запуск контейнера (`docker compose run --rm`), без требования устанавливать языковые рантаймы на хосте. Ограничения на глубину или размер `metadata` при необходимости задаются в плане реализации.
