# Исследование и решения: HTTP-приёмка событий

Контекст: фича `001-http-event-ingestion`, спецификация `/home/ubuntu/sonaka-event-tracker2/specs/001-http-event-ingestion/spec.md`, конституция `/home/ubuntu/sonaka-event-tracker2/.specify/memory/constitution.md`.

## 1. HTTP-сервер на Go

- **Decision**: использовать стандартную библиотеку `net/http` (Go 1.22+) без обязательной зависимости от веб-фреймворка; маршрут одного эндпоинта приёмки и health/readiness при необходимости реализуются через `http.ServeMux` или минимальную обёртку.
- **Rationale**: соответствует конституции (Go как сервер приложения), мало зависимостей, достаточно для одного JSON POST; проще сопровождать в контейнере.
- **Alternatives considered**: Chi/Echo/Fiber — отклонены как избыточные на этапе одного эндпоинта; при росте API их можно ввести отдельной задачей.

## 2. Драйвер PostgreSQL и работа с `database/sql`

- **Decision**: `github.com/jackc/pgx/v5` в режиме `stdlib` (`github.com/jackc/pgx/v5/stdlib`) для совместимости с `database/sql`, либо прямой pgx — в реализации выбрать один стиль и не смешивать; миграции — SQL-файлы через `github.com/golang-migrate/migrate/v4` с драйвером `postgres`.
- **Rationale**: pgx — распространённый и хорошо поддерживаемый драйвер для PostgreSQL; migrate — уже упоминался в проектных правилах и удобен для версионируемых SQL-миграций.
- **Alternatives considered**: `lib/pq` (режим поддержки только исправлений); ORM (GORM) — отклонён как лишняя абстракция для одной таблицы событий.

## 3. Ограничение размера тела запроса

- **Decision**: жёсткий лимит **1 MiB** на тело одного запроса приёмки; при превышении — отказ с HTTP `413 Payload Too Large` и JSON ошибки по контракту.
- **Rationale**: закрывает сценарий «слишком большой объём» из спека; значение достаточно для типичных метаданных и предсказуемо для эксплуатации.
- **Alternatives considered**: 256 KiB / 4 MiB — отклонены в пользу баланса между удобством клиентов и защитой сервиса; при необходимости вынести в переменную окружения.

## 4. Формат ошибок (машиночитаемый JSON)

- **Decision**: единая обёртка ошибки, например объект верхнего уровня с полем `error`: `{ "code": "<строковый_код>", "message": "<человекочитаемое>", "details": { ... } }` (поле `details` опционально для валидации полей). Коды HTTP: `400` для ошибок клиента (валидация, неверный Content-Type, невалидный JSON), `413` для превышения размера, `500`/`503` для сбоев БД/недоступности.
- **Rationale**: спек требует понятной индикации и машиночитаемости; единый формат упрощает клиентов и автотесты.
- **Alternatives considered**: текст/plain для ошибок — отклонён (не машиночитаемо); Problem Details (RFC 7807) — допустимо в будущем, на первом этапе достаточно простого JSON.

## 5. Парсинг `event_time` и fallback

- **Decision**: разбор через `time.RFC3339` и совместимые варианты ISO 8601, поддерживаемые пакетом `time` (при необходимости узкий дополнительный разбор); при неуспехе — сохранять `event_time` как время приёма на сервере (UTC), как в спеке и допущениях.
- **Rationale**: прямое следование FR-002 и разделу Assumptions.
- **Alternatives considered**: строгой отказ при плохом `event_time` — противоречит уточнённому поведению спека (вариант A).

## 6. Клиенты PHP и bash

- **Decision**: PHP 8.3+ — скрипт отправки через `curl` расширение или `file_get_contents` с HTTP-контекстом (предпочтительно явный `curl_*` или библиотека, если уже есть в образе); bash — `curl` с JSON из переменных/ heredoc. Запуск только через `docker compose exec` согласно документации.
- **Rationale**: соответствует конституции (PHP и bash-клиенты); curl в bash покрывает эталон без рантайма на хосте.
- **Alternatives considered**: только PHP без bash — отклонено конституцией.

## 7. Интеграционные автотесты

- **Decision**: автотесты на **PHP 8.3+** в каталоге `clients/php/tests/`, выполняемые **в сервисе `client-php`** (тот же контейнер, что и клиентские примеры): HTTP POST к эндпоинту приёмки сервиса `app` → чтение строки из PostgreSQL по `id` (например `PDO` с `pgsql`) с сравнением полей и нормализацией времени к UTC. Точка входа — один раннер (например `clients/php/tests/run_integration_tests.php`) или несколько сценарных скриптов; внешний фреймворк (PHPUnit) не обязателен на первом этапе.
- **Rationale**: FR-005 и конституция (автотесты в контейнерах); исходное требование проекта — тесты на PHP рядом с клиентами ([prompt.txt](../../prompt.txt)).
- **Alternatives considered**: `go test` в `tests/integration` — отклонено для этой фичи, чтобы не расходиться с контейнером клиентов и явным требованием PHP; только bash — хуже структурирование и отчётность; тяжёлый тестовый фреймворк — лишняя зависимость на старте.

## 8. Конфигурация и compose

- **Decision**: переменные `DATABASE_URL` или набор `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, URL базы для HTTP-клиента к приёмке (например `APP_URL` или `INGEST_BASE_URL`), `HTTP_ADDR` (например `:8080`) в `.env` и прокидывание в сервисы через `docker-compose.yml`; отдельные сервисы: `postgres`, `app` (Go), `client-php` (PHP-клиенты и **интеграционные тесты**), `client-bash`. Образ `client-php` должен включать драйвер PostgreSQL для PHP (`pdo_pgsql` или эквивалент), чтобы тесты могли выполнять проверочные `SELECT`.
- **Rationale**: принцип V конституции и правила workspace.
- **Alternatives considered**: хардкод учёток в образе — отклонён.
